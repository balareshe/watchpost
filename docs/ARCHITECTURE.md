# Watchpost 架构与设计取舍

这篇解释「为什么这么做」，以及每个选择付出的代价。想改架构之前先读一遍。

---

## 1. 数据存储：一个 JSON 文件，不用数据库

**选择**：业务数据（事件 / 公告 / 维护窗口 / 节点 / 用户 / 设置）全部存在
`/data/status-data.json`，写盘用 `临时文件 + os.replace` 原子替换，读时全量加载。

**为什么**

- 数据量极小：一年几百条事件，整个文件通常 < 100 KB；
- 零外部依赖：不需要跑 Postgres/MySQL，一台 1 核 1G 的机器就够；
- 备份和迁移就是拷一个文件；
- 出问题用 `cat` 就能看，不需要连客户端。

**代价**

- 所有写操作靠进程内 `threading.Lock` 串行化，**只支持单实例**；
- 每次读取都反序列化整个文件，数据涨到几万条后会变慢；
- 没有事务和查询能力，复杂统计要在 Python 里做。

**什么时候该换**：需要多副本 / 数据超过几 MB / 要做多维查询时，换成 SQLite（单机）或 Postgres（多副本），
并把 `load()/save()` 抽象替换成 DAO。

---

## 2. 后端：Python 标准库 `http.server`，不引框架

**选择**：`ThreadingHTTPServer` + 手写路由，零 pip 依赖。

**为什么**

- 镜像只有 Python 基础层，体积小、启动快；
- 不用维护依赖树，也不会有第三方库的 CVE 追着你；
- 逻辑量小（一个文件约 900 行），框架带来的收益有限。

**代价（都是真踩过的）**

- 要自己处理 keep-alive：**鉴权前必须读完请求体**，否则 401/403 时 body 留在连接里，
  被当作下一个请求行解析，出现 `{"email":...}GET /api/users → 501` 的诡异错误；
- 要自己处理路由匹配、JSON 解析、Content-Length、Cookie；
- 并发是线程模型，重活（发邮件）必须丢到后台线程，否则卡住请求。

**什么时候该换**：接口数量翻倍、需要 WebSocket/SSE、需要中间件生态时，换成 FastAPI/Flask。

---

## 3. 探针：交给 Gatus，不自己造

**选择**：实际探测与历史存储由 [Gatus](https://github.com/TwinProduction/gatus) 负责，
状态页只消费它的 API 与 SQLite。

**为什么**

- 成熟：HTTP/TCP/ICMP、条件表达式、30 秒级调度、历史聚合、失败事件记录，全都现成；
- 历史数据（`endpoint_events` / `endpoint_uptimes`）比自己维护轮子可靠；
- 出问题时可以用 Gatus 官方 UI 排查。

**代价**

- Gatus 配置是静态 YAML，**不支持运行时加节点** → 自定义节点只能由我们自己探测；
- 配置里 `ui.hide-url: true` 后 API 不返回 URL → 想做「失败后立刻重试」必须读配置文件拿 URL
  （因此 watcher 挂载了 `./config/gatus`）；仓库自带模板**没有**开这个开关，要藏 URL 得在部署配置里自己加；
- 自定义节点的地址同样不对匿名暴露（`GET /api/nodes` 匿名返回里没有 `url`）；
- 数据在 SQLite 且主要在 `-wal` 文件里，导出要注意。

---

## 4. 自定义节点：watcher 直接探测

**选择**：后台「节点」页加的自定义节点，由 `watch.py` 每轮直接发 HTTP 请求，
采样存 `watcher-state` 卷，输出 `/web/data/nodes.json`。

**为什么**

- 绕开 Gatus 不能热加节点的限制；
- 需求简单（HTTP 可达 + 延迟），不需要 Gatus 的全部能力。

**代价**

- 只有 24 小时采样（96 格），不像 Gatus 能查 7 天/30 天；
- 重启 watcher 后历史从零累积；
- 探测频率固定跟随 watcher 轮询（默认 60 秒），不能像 Gatus 那样每 30 秒。

---

## 5. 前台：原生 JS，不用 SPA

**选择**：`web/index.html` + `app.js`，无构建步骤，Caddy 直接托管。

**为什么**

- 首屏快：没有框架运行时，弱网下也秒开；
- 部署简单：改完直接生效，不需要 Node；
- 页面逻辑集中在「渲染列表 + 日历 + 事件」，规模可控。

**代价**

- 手写 DOM 更新，状态靠全局 `STORE` 对象；
- 逻辑再复杂就会难维护，届时应换成 Vue/Preact 构建版。

---

## 6. 后台：Vue 3 + Vite

**选择**：`admin-app/` 用 Vue 3 + Vue Router 构建，产物提交到 `web/admin/`。

**为什么**

- 后台有 10 个页面（概览、工单、事件、公告、维护、节点、用户、系统设置、通知、设置）、表单、角色控制、路由守卫，组件化收益明显；
- 构建产物是纯静态文件，部署机不需要 Node。

**代价**

- **产物必须与源码同步提交**，改了 `admin-app/` 不 `npm run build` 就等于没改；
- 多了一次构建步骤，CI 里必须跑。

---

## 7. 认证：邮箱验证码，不存密码

**选择**：管理员邮箱一次性验证码登录；会话用随机 `sid` Cookie；服务间用 `ADMIN_TOKEN` Bearer。

**为什么**

- 没有密码 = 没有密码哈希、没有撞库、没有重置流程；
- 邮箱本身就是管理员白名单（`ADMIN_EMAILS` + 用户表）；
- 自动化脚本用独立令牌，不受会话过期影响。

**关键参数**

| 项 | 值 | 目的 |
|---|---|---|
| 验证码 | 6 位，10 分钟有效 | 够用且不易爆破 |
| 错误次数 | 5 次作废 | 限制在线爆破 |
| 同邮箱发码冷却 | 60 秒 | 防刷收件箱 |
| 同邮箱每小时上限 | 5 次 | 防刷 |
| 同 IP 每小时上限 | 10 次 | 防批量 |
| 会话 | 32 字节随机，7 天，`HttpOnly; Secure; SameSite=Lax` | 防 XSS 读取、防 CSRF |
| 枚举防护 | 校验失败统一提示，不区分邮箱是否存在 | 不泄露管理员名单 |
| 服务令牌 | `ADMIN_TOKEN`，仅内部调用 | 人不用记 |

**代价**

- 依赖 SMTP；没配 SMTP 时只能用 `DEV_ECHO_CODE`（会把验证码回显到登录框，**生产禁用**）或翻日志；
- 会话存服务端 JSON 文件，重启不丢但也不跨实例共享。

**首次安装（v0.1.2 起）**：没有用户、没配 `ADMIN_EMAILS`、且从未初始化过时，`/admin/` 自动进安装向导。
安全设计是「默认关闭 + 一次性令牌」：

| 措施 | 作用 |
|---|---|
| 仅 `users` 为空 + 无 `ADMIN_EMAILS` + 无 `setupCompletedAt` 才开放 | 已初始化的实例永久关闭入口 |
| 初始化令牌 `token_urlsafe(24)`，只存内存、只打印日志 | 不落盘、不进接口返回值，重启即失效 |
| `hmac.compare_digest` 常数时间比对 | 防计时侧信道 |
| 单 IP 每小时 10 次 | 防爆破 |
| `complete_setup()` 二次校验 `users` 是否为空 | 并发抢注只有第一个能成功 |

为什么不做成「谁访问谁当管理员」：那等于给公网一个抢注后门，扫描器一旦发现就接管实例。
代价是用户首次仍要去日志里抄一个令牌——这是刻意的取舍，比门户大开安全得多。

## 8. 自动化：先重试再升级，慢响应只记录

**失败 → 开单的判定链**：

```
探测失败（Gatus 记一次）
   └─ 连续失败累计到 FAIL_THRESHOLD（默认 1）→ watcher 立即对该 URL 重试 3 次（间隔 2 秒）
        ├─ 任一次成功 → 视为抖动，不记录、不通知
        └─ 3 次全失败 → 升级为 critical（红），创建工单并发邮件
```

为什么要这一层：Gatus 30 秒一探，一次失败可能只是网络抖动；直接开单会产生大量噪音工单。
`FAIL_THRESHOLD` 想「先观察两轮再说」就调大（每多 1 等于多等一个轮询间隔）。

**恢复判定**：连续成功 3 次 → 自动追加「已恢复」并关单（同样为了避免一两次波动就关单）。

**慢响应**：连续 N 次（默认 3，后台「系统设置」里可改）超过阈值（全局 800ms，可按节点覆盖）→ 记一条 `minor` 事件，
**标记 `silent`，不发邮件、不弹横幅**，只进事件列表。理由是慢不等于坏，通知会变成噪音。
阈值填 0 即关闭慢响应判定；后端判定与前台标黄读的是同一份设置，不会各说各话。

**维护窗口**：窗口内既不重试也不自动开单，避免计划内操作被当成故障。

## 9. 事件状态机

```
investigating（排查中）
      ↓
identified（已定位）→ in_progress（修复中）
      ↓                       ↓
monitoring（监控中） ←────────┘
      ↓
resolved（已恢复，写入 resolvedAt）
```

- 允许跳级（比如直接从排查中到已恢复）；
- 每次状态变更都会追加一条「更新记录」，前台时间线按时间倒序展示；
- 删除用户时会同步清掉其会话，停用则不删历史。

## 10. 严重程度与展示

| 值 | 文案 | 颜色 | 用途 |
|---|---|---|---|
| `critical` | 重大 | 红 | 核心不可用 |
| `major` | 严重 | 红 | 主要功能受影响 |
| `minor` | 一般 | 橙/黄 | 部分异常、慢响应 |
| `info` | 提示 | 灰 | 不影响使用 |
| `maintenance` | 维护 | 蓝 | 计划内变更 |

兼容旧值：`down → critical`、`warn → minor`。

**「重大」的判定门槛**：采集器从 Gatus 事件推断事故时，**持续时间 < `CRITICAL_MIN_SEC`（默认 90 秒）的降级为「一般」**。
原因：Gatus 每次探测失败都会记一条 `UNHEALTHY` 事件，单次抖动的事件时长最多等于一个探测间隔（30/60 秒），
如果直接标红，就会出现「显示重大但没有工单、也没发邮件」——因为 Watcher 重试后判定为抖动、按设计不开单。
降级后规则变得一致：**红色 = 持续 ≥90 秒（约 3 次连续失败）= Watcher 必然已开单并发过邮件**。

**日历配色**按「当天出现过什么级别的事件」决定，而不是按可用率百分比：
有红级事件 → 红；只有黄级 → 黄；无事件且有数据 → 绿；无数据 → 灰。
（按百分比算会出现「99.51% 全绿但当天确实挂过」的观感问题。）

## 11. API 约定

| 集合 | 公开读 | 写 | 说明 |
|---|---|---|---|
| `incidents` | ✅ | 管理员 / 维护人员 | 事件工单 |
| `announcements` | ✅ | 同上 | 公告 |
| `maintenance` | ✅ | 同上 | 维护窗口 |
| `nodes` | ✅（不含 url） | 同上 | 节点与排序；匿名读会剥掉 `url` 字段 |
| `users` | ❌ | **仅管理员** | 账号管理 |
| `settings` | 部分子集 | **仅管理员** | 站点信息 / 通知 / 模板 |
| `setup` | 仅未初始化时 | 未初始化时可用（需一次性令牌） | 首次安装：建管理员 + 写 SMTP |

鉴权分三级：`read`（登录即可）、`write`（管理员或维护人员）、`admin`（仅管理员）。
服务令牌（`ADMIN_TOKEN`）可越过所有级别，供 watcher 使用。

错误码：`400` 参数问题、`401` 未登录、`403` 权限不足、`404` 不存在、`429` 频率限制。

## 12. 部署形态

- 5 个容器：`caddy`（入口）、`status-api`、`status-watcher`、`status-collector`、`gatus`；
- 后端代码来自 GHCR 镜像 `ghcr.io/balareshe/watchpost-core`（api/watcher/collector 共用）；
- `web/`、`config/`、`caddy/` 仍以挂载提供 —— 改探针、改前端不必重建镜像；
- 数据在 5 个命名卷里，`down` 不丢、`down -v` 会丢。

## 13. 已知边界与扩展方向

| 限制 | 现状 | 扩展方向 |
|---|---|---|
| 单实例 | 进程内锁 + 单 JSON | 换 SQLite/Postgres，锁移到 DB |
| 监控端单点 | 无自监控 | 外部探活（第三方）+ 面板心跳警示 |
| 无主机指标 | 只做可达性 | 受限 SSH 只读命令，或 node_exporter（需接受常驻进程） |
| 慢响应只有一段阈值 | 全局 + 单节点 | 可做分位数/滑动窗口 |
| 通知只有邮件 | `notify_incident()` | 抽成 provider：Webhook / IM / SMS |
| 日历固定 4 周 | 按自然周 | 改为滚动 28 天（今天固定在最后一格） |
